# Decision log (ADR-lite)

Append-only. One entry per decision that changes or clarifies the spec. Format: `## ADR-NNN — Title (YYYY-MM-DD)` + Context / Decision / Consequences, 3–8 lines total.

## ADR-001 — Rust instead of Go (2026-10-12)
Context: the draft proposed Go with a < 30 ms target. Pulse scans untrusted text with many patterns, on every commit and keystroke.
Decision: Rust 2024. It provides the ripgrep-grade crates `ignore`, `globset`, `regex` (linear time, no ReDoS), `aho-corasick` (SIMD multi-pattern) and `memchr`, ~1 ms startup, no GC, and a single static binary.
Consequences: compile times are slower than Go (mitigated by a 5-crate workspace and incremental builds). The npm/pip/brew distribution story is the same as for Go (prebuilt binaries via cargo-dist).

## ADR-002 — Deterministic, offline core (2026-10-12)
Decision: no network and no LLM calls in the core. A semantic `--deep` mode (LLM-assisted contradiction and ambiguity analysis) may come later as an opt-in feature behind a cargo feature flag.
Consequences: heuristic COG rules default to Low/Medium severities and favor precision.

## ADR-003 — Five-crate workspace (2026-10-12)
Decision: `pulse-core`, `pulse-rules`, `pulse-engine`, `pulse-report`, `pulse-cli`. Rules change most often, so they are isolated for incremental compile and focused context. The engine is a library so a future LSP/WASM build can reuse it.

## ADR-004 — Rule IDs `AI-<CAT>-<NNN>` with four categories (2026-10-12)
Decision: keep the draft's `AI-` prefix. Categories SEC/STR/EFF/COG map to Sonar types Vulnerability/Bug/Code smell. STR was added for validity bugs (frontmatter, schemas, broken refs). Custom rules use `X-<ORG>-<NNN>`.

## ADR-005 — Heuristic token estimation (2026-10-12)
Decision: `max(chars/4, words*1.3) * calibration`, with code at 3.2 chars/token. There is no public Claude tokenizer, and bundling BPE vocabularies adds MBs and slows startup. An optional `tiktoken` feature can come later.

## ADR-006 — Critical security findings are not inline-suppressible (2026-10-12)
Context: the scanned assets may themselves be attacker-controlled. A planted `<!-- pulse-ignore AI-SEC-002 -->` would otherwise defeat the scan.
Decision: AI-SEC-001/002/003/008/012 can only be suppressed through `pulse.toml` `[[ignore]]`, which lives in reviewed config.

## ADR-007 — Severity scale and ratings (2026-10-12)
Decision: Critical/High/Medium/Low/Info (the draft's scale, not Sonar's Blocker/Major/Minor). Security/Reliability/Clarity ratings use the worst open severity; Efficiency uses the context-debt ratio (see 04-scoring-gate.md).

## ADR-008 — Windows in CI from Phase 0 (2026-10-12)
Context: P0.1 specified CI on ubuntu + macos only, but Phase 7 ships a Windows x64 binary.
Decision: the CI matrix includes `windows-latest`, running `scripts/check.sh` under Git Bash. `.gitattributes` forces LF checkout so fmt, snapshots and fixtures behave the same on every OS; CRLF test input is generated in code.

## ADR-009 — Discovery clarifications (2026-10-12)
Context: P1.1 found gaps in 02-assets: the kind of `scan.include` matches, custom vs built-in priority, and ignore-file scope.
Decision: built-in rows win, then `[[scan.custom]]`, then `scan.include` (Custom, OnDemand). Ignore files apply from the scan root down (`require_git(false)`, `parents(false)`); ancestors' and the global gitignore are ignored for cross-machine determinism. Unfollowed symlinks count as existing paths but are not analyzed. `.claude/CLAUDE.md` is root-level (Always). Truncated `tools/*.json` sniffing falls back to a key scan.
Consequences: a custom glob cannot reclassify a built-in asset; users who rely on a global gitignore must use `.pulseignore` or `scan.exclude`.

## ADR-010 — Text utility clarifications (2026-10-12)
Context: P1.2 found gaps in "Token estimation" and "Text normalization" (02-assets): what counts as a word separator, how NFKC interacts with the offset map, and how a normalized range maps back to an end offset.
Decision: the token estimator splits words on ASCII whitespace only (byte loop, no decoding). Normalization runs NFKC per segment (a starter plus its trailing non-starters), so every output byte maps to the segment's first source byte; Hangul jamo composition across starters is not applied. `map` carries a trailing sentinel equal to the source length, and `source_span` extends the end to the next source unit, so dropped characters after a match fold into its span.
Consequences: exotic Unicode spaces don't split words for token estimates; source spans may include trailing invisibles, which is harmless for reporting.

## ADR-011 — Markdown view clarifications (2026-10-12)
Context: P1.3 found gaps in "Per-kind parsed views" (02-assets): unterminated frontmatter, `@import` edge cases, key-line map type, and where frontmatter promotion lives.
Decision: a `---` opener with no closing `---` line is not frontmatter (the file is all body). Frontmatter that is valid YAML but not a mapping is `Err`; YAML error messages drop the YAML-relative `at line N column M` marks, and `line` is file-relative. Alias expansion relies on serde_yaml_ng's repetition limit, which surfaces as `Err`. `key_lines` is a `BTreeMap` (deterministic iteration). `@path` imports are skipped inside code, raw HTML and links, and after a word char, `/`, `:` or `=` (emails, bare URLs, attributes); trailing dots are trimmed. ScopedInstructions promotion is computed by `Asset::effective_load()` (discovery keeps the path-only mode) and applies only when the discovered mode is Conditional; invalid YAML keeps Conditional. `Asset::with_calibration` sets the factor for `tokens()`.
Consequences: an unclosed frontmatter is not reported as a YAML error. A `@handle` mention in prose still counts as an import (as the spec's pattern implies).

## ADR-012 — JSON view clarifications (2026-10-12)
Context: P1.4 found gaps in "Per-kind parsed views" (02-assets): `jsonc-parser`'s AST borrows the source (an `Asset` can't hold it), the MCP transport shape, hook files that aren't Claude settings, and the cost of a full pointer index.
Decision: `JsonDoc` converts the AST into an owned `JsonNode` tree with byte spans (lenient `ParseOptions::default()`; a syntax error is one `ViewError`, and the root is `None`). Pointer lookups (`span_of`, `key_span_of`) walk the tree; the full pointer → span maps (`pointer_spans()`) are built only on first use. `McpServer` keeps `args`/`env`/`headers` flat beside a `Transport` enum (`Stdio{command}`, `Http{url}`, `Sse{url}`, `Unknown`); `httpUrl` (Gemini) and `serverUrl` (Windsurf) are URLs, and an explicit `type` without its endpoint is a shape error. Hooks assets reuse `SettingsView` (`Asset::hooks()`); Cursor's flat `{command}` entries become a matcher-less `HookEntry`. Hook types other than `command`/`prompt` (`http`, `agent`, …) have an empty command whose span covers the hook. Tools are read from a root array or a root `tools` key, in Anthropic, OpenAI-nested and OpenAI-flat forms. Duplicate keys: the last one wins.
Consequences: views report only shape errors; AI-STR-002 reads syntax errors from `Asset::json().errors`.

## ADR-013 — Engine pipeline clarifications (2026-10-12)
Context: P2.1 found gaps in "Data flow" and "Key types" (01-architecture): where per-rule options are validated, how skipped files reach AI-STR-002, which assets project rules see under a path filter, and what "always-on" means per kind.
Decision: `RuleCtx.options` is an `OptionsStore` (all `[rules.<ID>]` tables; typed parses cached per (rule, type)); `Rule`/`ProjectRule` gain a default `validate(&ctx)` that the engine calls once per enabled rule before any check, so bad options abort the scan as `EngineError::Config`. Oversized or unreadable files become `Asset::skipped(reason)` (empty source) and only AI-STR-002 runs on them; invalid UTF-8 is decoded lossily with `Asset.lossy = true`. With `ScanOptions.paths`, asset rules run only on matching assets, project rules see every asset, and all findings are filtered by path; `assets_meta` always lists every asset. A `[rules]` severity override applies to every finding of the rule (the Info "skipped" finding included). Dedup merges across rules only: per (location, category) it keeps the rule with the highest-severity finding (ties to the lowest rule ID) and all of that rule's findings there; custom-rule findings are never merged. Files are read with one bounded read (`max_file_bytes + 1`), and rule options are validated before discovery. `Asset::always_tokens()`: the frontmatter `description` for skills/agents, 0 for MCP configs, settings and hooks, the whole file for other Always assets. `Report.walk_errors` carries the walker's unreadable entries.
Consequences: path-filtered CI scans keep project-wide budgets meaningful. Overriding AI-STR-002's severity also raises skipped-file notices.

## ADR-014 — AI-SEC-001 clarifications (2026-10-13)
Context: P2.2 found gaps in "AI-SEC-001" (03-rules) and "Rule fixture harness" (07-testing): message format for mixed and tag runs, which emoji bases the guards accept, and the harness demanding a committed `fail_*` file while invisible content must be generated in code.
Decision: one finding per contiguous run; `(×N)` only when N > 1, `and others` when the run mixes code points; runs containing tag characters report `Hidden tag text (×N): "<payload>"` (printable tags only, 80-char cap). The ZWJ guard needs non-ASCII emoji on both sides; a variation selector is allowed after any emoji base, ASCII keycap bases included, and an allowed selector or ZWJ keeps the emoji sequence going. The pre-filter is `memchr3` + `memchr2` over the five lead bytes, then a char walk from the first hit. A `_generated` file in a fixture dir stands in for `fail_*` when all fail cases are generated in `fixtures.rs`.
Consequences: emoji tag sequences (subdivision flags) are still reported; tracked in the Backlog. Tag-run messages can slightly exceed the 100-char guideline.

## ADR-015 — AI-COG-001 clarifications (2026-10-14)
Context: P2.5 found gaps in "AI-COG-001" (03-rules): how to cache directives, what "skip inline code" means for objects, how "same object" compares objects of different lengths, and when a heading "names a scope".
Decision: `cognitive::directives::extract(asset)` is a pure function that each rule calls; nothing is cached, because AI-COG-001 runs once per asset and AI-COG-005 will extract from each asset once. If AI-COG-005 compares one asset against several others, it should extract each asset once into a local map rather than add a cache to `Asset`. `Prepared` precomputes each directive's section scope and exclusive-set members, so the pairwise loop does no allocation or lexicon scans. Code blocks, HTML comments and headings are skipped; inline code only blocks sentence splitting, and its text stays in the sentence (`Never use \`any\``). A `do` directly followed by a negator opens a negative directive anywhere in the sentence ("We do not use yarn"). The verbs use/using/prefer/avoid and verb-less markers (`No semicolons`) count as the verb `use`. A directive's context is the content words after its first qualifier (`for`, `in`, `when`, …) outside the verb and object, and two directives with different contexts never conflict. For opposite polarity, the negative object must be a prefix of the positive object, so "Never use semicolons" contradicts "Always use semicolons at the end", but "Never use TypeScript enums" only narrows "Always use TypeScript". The section guard applies only when both nearest headings name scopes, meaning at least one word is not in `GENERIC_HEADINGS`, and the headings differ. Each directive gets at most one finding, against the first earlier directive it conflicts with. Quotes are cut to 34 chars so the message stays within 100.
Consequences: a file-title heading such as "# Acme assistant" names a scope, so a directive above the first `##` is not compared with directives in scoped `##` sections. Same-polarity duplicates and paraphrases ("Never use X" / "Avoid X" are equal) produce no finding.

## ADR-016 — Suppression clarifications (2026-10-15)
Context: P2.6 found gaps in "Inline suppressions" (05-cli-config): malformed comments, stacked next-line comments, multi-line findings, the order relative to dedup, and whether `ignore.rules` is validated.
Decision: a suppression matches findings whose start line is its target. A next-line comment skips blank lines and lines that hold only another suppression comment. A comment that lists no IDs or `all`, or a `pulse-ignore-file` after the first heading, becomes an Info AI-STR-002 `invalid suppression: …` finding. Unused-suppression notes name the ID and are emitted only for rules that ran, so a rule disabled by config or `--only`/`--skip` doesn't produce false notes. All notes are skipped when AI-STR-002 is off. Suppression runs after severity overrides and before dedup, so suppressing one rule never hides another rule's finding on the same span. `[[ignore]]` runs after the inline pass and may drop notes. Unknown rule IDs in `ignore.rules` are config errors, like `[rules]`. An unknown ID in an inline comment becomes `invalid suppression: unknown rule <ID>`, except for `X-` IDs, which are left to custom rules. Next-line targets are resolved in one reverse pass over the lines, so hostile files full of stacked comments stay linear. `Report.suppressed` counts every dropped finding, notes included.
Consequences: a multi-line finding is suppressed only from its first line. Custom-rule suppressions are never reported as unused until custom rules run.

## ADR-017 — Scoring & gate clarifications (2026-10-15)
Context: P2.7 found gaps in 04-scoring-gate: how custom rules map to ratings, what "overlapping waste" means for findings that carry locations rather than spans, and how disabled gate conditions are shown.
Decision: a finding's category comes from its `AI-<PREFIX>-` rule ID, so custom `X-` rules have no category and affect no rating (they still count in `fail_on_severity`). Waste overlaps when two EFF findings in one file have intersecting half-open location ranges; each overlapping cluster contributes its max waste. Disabled gate conditions are omitted from `Gate.conditions`. Metrics cover in-scope assets only. Condition values are typed (`GateValue`) and formatted by the reporters.
Consequences: a project of only custom-rule findings rates A everywhere but can still fail the gate through `fail_on_severity`.

## ADR-018 — CLI flag details for `scan`/`ci` (2026-10-15)
Context: P2.8 wired `scan`/`ci`; the Commands section left `-v`, `PATHS` resolution and color precedence implicit.
Decision: `-v, --verbose` is a global flag (remediation for every finding in the terminal report). `PATHS` are root-relative (absolute paths under the root are stripped). An explicit `--color` wins over `NO_COLOR`; `ci` treats `--color auto` as off. `init` uses the global `-C`. Formats without a reporter yet (`json`, `sarif`, `markdown`) exit 2 with "not implemented yet"; `github` renders as terminal until P6.2.
Consequences: `pulse -C dir scan sub/` scans `dir/sub`, not `./sub`; `--new-only`/`--changed-since` are added with their implementation in P6.3.

## ADR-019 — v0.1.0 performance numbers miss the budget on Intel hardware (2026-10-15)
Context: P2.9 ran `scripts/bench.sh` on the only machine available, a 2019 Intel i5-8257U MacBook Pro. The budgets in 00-overview are defined on Apple M-series. Medians: startup 6.1 ms (budget 2), typical 45.7 ms (20), large 316.7 ms (150). Peak RSS (8.2 MB) and binary size (2.8 MB) are within budget.
Decision: v0.1.0 ships with these numbers, and the budgets stay unchanged. On this machine the gap is in the hardware and the OS, not in Pulse: spawning `/usr/bin/true` takes 4.2 ms, and `rg --files` (the same parallel `ignore` walker) needs 40 ms and 380 ms to list the two trees, which is slower than a full Pulse scan of them. Discovery takes about 80% of scan time (`--timings`: discover 28 ms of 37 ms on typical, 190 ms of 225 ms on large). The Perl timing fallback in `bench.sh` replaces a `/usr/bin/time` loop, because `/usr/bin/time` reports only 10 ms resolution.
Consequences: P7.1 must re-measure on Apple M-series hardware (or a `macos-14` arm64 CI runner) before deciding whether the walk needs work. `bench.sh` exits 1 on this machine until then.

## ADR-020 — AI-SEC-003 generic pattern and placeholder guards (2026-10-15)
Context: P3.1 implemented AI-SEC-003. The spec's generic regex `(api[_-]?key|token|secret|password)\s*[:=]…` misses JSON keys (`"apiKey": "…"`, the closing quote sits before the colon) and suffixed keys (`aws_secret_access_key = …`), and its placeholder list has no entry for environment lookups other than `${…}`.
Decision: the generic key may carry a `[a-z_]*` suffix and a closing quote before `:`/`=`, with only spaces or tabs around the separator; matching is case-insensitive and has no leading word boundary (so `OPENAI_API_KEY=` matches). Placeholders also cover `$VAR`, `{{…}}`, `placeholder`, `redacted`, `process.env`, `environ`, `getenv`; "all-same-char" is read as "one character makes up at least half of the value". Two shape guards beyond the spec: an OpenAI match needs upper case, lower case and a digit (kebab-case slugs like `sk-learn-…` are not keys), and a generic value needs a digit and must not look like code (calls, indexing, dotted paths such as `settings.SECRET_KEY`). Overlapping matches keep the earliest start, then the first pattern in `lexicon/secrets.rs` order (Anthropic before OpenAI, providers before generic). The finding's span is the secret value only.
Consequences: AI-SEC-004 must report on the value span (without quotes) so the engine's same-span dedup lets AI-SEC-003 win.

## ADR-021 — MCP security rule details (2026-10-15)
Context: P3.2 implemented AI-SEC-004/005/006. The spec leaves value guards, version exactness and non-registry specs open.
Decision: AI-SEC-004 treats a value as externalized when it contains a reference anywhere (`Bearer ${input:X}`), (`$NAME` counts only at the start or after whitespace, so `pa$word` stays literal), and also skips AI-SEC-003 placeholders, switches/numbers (`true`, `off`, `4096`), file paths and URLs without userinfo; keys ending in `file`, `path`, `dir`, `url`, `uri`, `type`, `enabled` or `mode` are not credential keys (`API_KEY_FILE`, `AUTH_URL`, `--key-file`), because the spec's unanchored regex matches them; Docker `-e KEY=value` / `--env=KEY=value` args are checked like `env` entries; its span is the value without quotes, and messages never quote the value. AI-SEC-005 calls a package pinned only with an exact semver (npm) or a `==` version without range operators / an `@MAJOR.MINOR.PATCH`-like version (Python); npm partial versions (`@1`) and dist-tags are unpinned; Docker accepts any non-`latest` tag or a digest as the spec says. `--package`/`--from`/`--spec` values are the packages when present, else the first positional; `uv tool run` is treated as `uvx`. Local paths, URLs, `git+`/protocol specs and variable references are not checked by AI-SEC-005, nor variable hosts by AI-SEC-006, which also treats all of `127.0.0.0/8` as loopback.
Consequences: fewer false positives on feature flags and templated configs; a config can still pull an unreviewed git ref (out of scope).

## ADR-022 — AI-SEC-007 scope and matching (2026-10-15)
Context: P3.3 implemented AI-SEC-007. The spec lists four kinds but also says the bypass flags are detected in "any asset", and leaves "write/exec tools" and "network tools" open.
Decision: the rule's `kinds` is every kind; settings, frontmatter and auto-approve checks run only on their kinds, the `--dangerously-skip-permissions` / `--yolo` search on all (as a whole flag, so `--yolo-mode` does not match). Unrestricted Bash in frontmatter is `Bash`, `Bash(*)` or `Bash(:*)` in `tools` or `allowed-tools` (comma string or YAML list); the network tools are `WebFetch` and `WebSearch`. `WebFetch(*)` counts as `WebFetch` without a domain. Only `permissions.allow` is checked (`deny`/`ask` are safe). An MCP tool is write/exec when a word of its name (split on `_`, `-`, `.` and camelCase) is in `lexicon/permissions.rs` (`write`, `exec`, `run`, `delete`, `push`, …). One finding per offending entry.
Consequences: Copilot tool names (`runCommands`, `fetch`) in `.prompt.md` frontmatter are not mapped to Bash/network yet; agents without a `tools` key (which inherit every tool) are not flagged.

## ADR-023 — Hook command scanning (AI-SEC-008/009) (2026-10-15)
Context: P3.4 implemented AI-SEC-008/009 on a small shell-word scanner (`security/shell.rs`: quotes, `$VAR`/`${…}`/`$(…)`/backticks/`<(…)`, pipes and separators; no here-docs or control flow). The spec's pipe-to-shell regex only accepts the shell right after the first pipe and does not say which fences count or what "tool input" covers.
Decision: AI-SEC-008 scans command hooks, every `bash`/`sh`/`shell`/`zsh` fence of a skill or prompt (not only those with `!` execution) and `` !`cmd` `` lines outside fences. Pipe-to-shell matches a downloader (`curl`, `wget`, `iwr`, `irm`, `Invoke-WebRequest`, `Invoke-RestMethod`) or a `base64 -d` stage followed by any later stage whose shell reads stdin; an interpreter with a script argument or a code flag (`-c`, `-m`, `-e`, …) is not reading stdin unless `-s` is given. Substitutions holding a downloader are flagged when run by a shell or `eval`/`source`/`.`/`iex`, and quoted `sh -c '…'` scripts are rescanned. AI-SEC-009 treats `$CLAUDE_FILE_PATHS`, `$CLAUDE_TOOL_INPUT` and substitutions mentioning `tool_input` as tool input, propagates it through `NAME=` assignments, and flags it unquoted, passed to `eval`/`source`/`sh -c` (quoted or not), or piped from a tool-input stage into `xargs` (with any flags). Prompt hooks are not shell and are skipped.
Consequences: `for f in $CLAUDE_FILE_PATHS` is flagged (word splitting is the risk); `while read` loops and `jq … | sh` style taint through stdin are not tracked.

## ADR-024 — Exfiltration and hidden-instruction heuristics (AI-SEC-010/011) (2026-10-15)
Context: P3.5 implemented AI-SEC-010/011. The spec's word lists and placeholder forms are loose: common docs ("Request an API key from https://…", "Agents may share the token", README badges `https://github.com/{owner}/{repo}/…/badge.svg`) would be High findings.
Decision: AI-SEC-010 (a) counts placeholders in a URL's host, query or fragment for links and images; in an image path only `{{…}}`, `$X`, `<…>` (and `%24`/`%3C`) count. (b) needs a send verb (`send`, `post`, `upload`, `exfiltrate`, `forward`, `transmit`, `leak`, `email`, `submit`, or `include`/`embed`/… with a URL word) that opens its clause after only leader words (`then`, `always`, `you must`, …), a sensitive object after it and before an instrument word (`using`, `with`, `via`), and no negator in the three words before the verb (`never forget`/`do not hesitate` don't negate); `token` followed by `usage`/`count`/… isn't sensitive. (c) needs a fetch word, a non-allowed URL and a data flag or templated URL. A host is taken after any `user@` and without its port. Tool descriptions get (b), (c) and Markdown images, one finding per tool. AI-SEC-011 checks a comment for injection phrases before any guard, so a `pulse-ignore`/`Copyright` prefix can't launder one; the tool-directive guard is a prefix match, generated/license guards are substring matches. Template verbs (`add`, `update`, `edit`, `replace`, `fill`) are not in `IMPERATIVES`. Hidden HTML parses each tag's attributes (`hidden`, `style` with `display:none`, `visibility:hidden`, `font-size:0`). Base64 needs ≥ 40 chars mixing upper case, lower case and digits, few `/`, not glued to `-_.@` and not in a code block, link or URL; whitespace padding is reported at the text after it. `MarkdownView` gains `html` (raw HTML spans).
Consequences: descriptive exfiltration ("this skill sends your token to …") and protocol-relative URLs are missed; comment directives with `use`/`run`/`read` still fire, as the spec intends.

## ADR-025 — Frontmatter schemas (AI-STR-001/004) (2026-10-16)
Context: P4.1 implemented AI-STR-001/004. AI-STR-002 already reports invalid YAML frontmatter, the spec names required keys only for some flavors, and leaves the known-key lists and the "reserved word" match open.
Decision: AI-STR-001 does not report YAML parse errors (AI-STR-002 owns them, avoiding a double High). An unterminated `---` (no frontmatter per ADR-011) is reported at line 1; a file without frontmatter is reported only when its schema has required keys; a null required value counts as missing. Schemas live in `structure/schemas.rs`, picked by kind and path suffix: any `SKILL.md` is a Claude skill, an Agent not ending in `.agent.md`/`.chatmode.md` is a Claude agent, a Prompt ending in `.md` but not `.prompt.md` is a Claude command (same keys as skills, none required); `.prompty`, `.claude/rules`, Windsurf and Cline files have no schema. The typo hint is the closest known key within 2 edits (first in table order on ties). AI-STR-004 matches `anthropic`/`claude` as substrings of the name (as the platform does), skips the directory check for a root-level `SKILL.md`, and checks `description` length on the trimmed value; agent and prompt names are free-form.
Consequences: known-key tables must follow platform changes, or new keys show up as Low findings.

## ADR-026 — Hook events and tool lists (AI-STR-005/006) (2026-10-16)
Context: P4.2 implemented AI-STR-005/006. The spec's hook types ({`command`, `prompt`}) and the task card's event list predate current Claude Code, which documents 33 events and the `http`, `mcp_tool` and `agent` hook types; Cursor's `.cursor/hooks.json` uses its own camelCase events. MCP servers are often configured per user (`~/.claude.json`), outside the scan, and VS Code extensions contribute Copilot tools no list can know.
Decision: `lexicon/platform.rs` holds per-platform lists checked against the Claude Code and Cursor docs on 2026-10-16 (Claude tools include older names such as `Task`, `MultiEdit`, `LS`). AI-STR-006 picks Cursor lists for paths under `.cursor/`, else Claude; matchers are JavaScript regexes, so only those with regex metacharacters are compiled (user content, size-capped) and look-around/backreferences are skipped; a missing `command` is no longer an AI-STR-002 shape error (the settings view keeps the hook with an empty command and AI-STR-006 reports it, avoiding a double High). Script paths resolve against the project root (the directory holding `.claude/`/`.cursor/`) or, for `hooks/hooks.json`, the plugin root; a path the walker did not see is looked up on disk, so gitignored scripts are not reported. AI-STR-005 is a project rule: Claude entries are checked against a closed list; an `mcp__<server>__…` entry needs `<server>` (non-`[A-Za-z0-9_-]` mapped to `_`) in some McpConfig, but is not checked when the project has none, nor for `ide`, `claude_ai_*`, `plugin_*` or wildcard servers. Copilot entries are reported only one edit from a built-in tool; tool sets (`x/y`) and MCP server names pass. Suggestions use the shared Levenshtein (ASCII case-insensitive, within a third of the word, 1..=3 edits).
Consequences: platform lists need updating as vendors add events and tools, or new names show up as High (events) or Medium (tools) findings; misspelled Copilot extension tools and MCP tools of user-scoped servers are missed.

## ADR-027 — References and the import graph (AI-STR-003, AI-EFF-002) (2026-10-16)
Context: the spec doesn't say which `@` tokens are files, how cycles are reported, or how imported files reach the always-on total.
Decision: `pulse-core::refs` resolves paths (relative to the referencing file; leading `/` = scan root; `~` and root-escaping paths are not checked). An `@` token is a file import only if it contains `/` or `.` (`@alice` is a mention). The engine builds one `ImportGraph` (Markdown assets' imports plus imported walked non-asset files, read once under `scan.max_file_bytes`, followed up to 5 hops) and passes it in `RuleCtx::imports`. A reference exists if it is a walked file, a walked directory prefix, or exists on disk (excluded files). Every import in a cycle of ≤ 5 hops is reported (High). Skill paths may resolve from the skill folder or the scan root (project skills name root scripts). The example-path guard (`<`, `your-`, `example`) applies to all references, not only fenced ones. AI-EFF-002 adds, once each, files reachable from always-on Instructions/ScopedInstructions minus their own always tokens; an imported contributor is reported at the root's `@import`.
Consequences: oversized or unreadable imported files count 0 tokens. Imports are not followed from skills, prompts or agents for token totals.

## ADR-028 — Invocation names and namespaces (AI-STR-007) (2026-10-16)
Context: the spec says "same kind and platform" but doesn't define the platform of a path, names without frontmatter, or plugins, whose skills are namespaced by the plugin.
Decision: the name is the frontmatter `name` (trimmed), else the skill folder or file stem (`.agent.md`, `.chatmode.md`, `.prompt.md`, `.md` stripped); Claude commands always use their path under `.claude/commands/` with `/` → `:`. `.prompty` files have no name. The namespace is the first platform directory in the path (`.agents`, `.claude`, `.codex`, `.cursor`, `.gemini`, `.github`, `.windsurf`), so nested `pkg/.claude/…` assets share it with the root ones; otherwise it is the grandparent directory of the asset (`plugins/a/skills`). "First" is the first in path order.
Consequences: skills and commands that both answer to `/x` on Claude are not reported (different kinds). Two monorepo packages that each define `.claude/skills/x` are reported, even if never loaded together.

## ADR-029 — MinHash instead of SimHash for duplicated content (AI-EFF-003) (2026-10-17)
Context: the spec asked for a 64-bit SimHash per paragraph with Hamming ≤ 3, bucketed by 4×16-bit LSH bands. Measured on a 39-word paragraph with 5-word shingles, changing a single word moves the SimHash by 7–13 bits (two words: 9–14), because one word touches 5 of ~35 shingles and a 64-bit SimHash only reaches ≤ 3 bits when ~99% of the features match. Hamming ≤ 3 therefore finds only exact copies, failing the card's "lightly reworded paragraph" case, and widening the threshold breaks the 4×16 band guarantee.
Decision: `pulse-core::text::shingles` keeps the 5-word shingles over normalized text (words hashed with xxh3; a shingle is a rotate-xor of its 5 word hashes through the murmur3 finalizer) and builds a one-permutation MinHash of 32 bins (top 5 bits pick the bin, the low 32 bits compete for its minimum; empty bins are filled by optimal densification from a fixed hash sequence). AI-EFF-003 fingerprints assets in parallel (rayon, already in the dependency table; each asset's words are hashed once and paragraphs/lines are slices), buckets paragraphs by 8 single-bin LSH bands (one identity-hashed map with newest-first chains, ≤ 64 members examined per band; a pair at Jaccard 0.5 shares a band with p ≈ 0.996), and confirms a pair when ≥ 16 of 32 bins agree (estimated Jaccard ≥ 0.5; one or two reworded words in 40 give about 19–25, same-topic paragraphs about 0). "Duplicate" when the normalized word sequences are identical, "Near-duplicate" otherwise. FP guard: assets are compared only when one's context root contains the other's, so sibling monorepo packages that are never loaded together don't match. Exact lines use an order-sensitive hash of the word hashes, only across always-on assets (not skills/agents), skipping fenced code, frontmatter and lines inside reported paragraphs. The k-function MinHash that was tried first cost 87 ms for the 1,000 × 20 bench on the i5-8257U (ADR-019). The one-permutation version, with parallel fingerprints, takes a median 10.9 ms there with the machine idle (34 ms on one thread; 17–35 ms while swapping), so about 3–5 ms on the M-series reference by ADR-019's ratio. The < 10 ms target needs re-measuring on M-series with P7.1.
Consequences: the threshold is probabilistic: pairs near Jaccard 0.5 may or may not be reported (deterministically, given the fixed functions). Heavily rewritten or merged paragraphs (Jaccard < 0.5) are missed. Very large buckets of identical text are capped at 64 examined members per band.

## ADR-030 — Bulk, sprawl and oversized thresholds (AI-EFF-004/005/006) (2026-10-19)
Context: the spec doesn't say whether a JSON/YAML "dump" is fenced, what counts as an enabled server across several clients' configs, or how a project's duplicate servers are identified; it names the tool limit `budgets.tools`, which is the Tools token budget (the count is `budgets.tools_count`).
Decision: AI-EFF-004 counts content lines (fences excluded); a `json`/`jsonc`/`json5`/`yaml`/`yml` block is a data dump and gets the 60-line limit instead of 40; tables count body rows (the Markdown view now records GFM tables). Skills and agents are excluded (their bodies are on demand). AI-EFF-005 counts distinct server names over all McpConfigs, so one server configured for Claude and VS Code counts once; `"disabled": true` or `"enabled": false` (now in the MCP view) excludes a server. Duplicates compare the command's file name (lowercase, `.exe`/`.cmd` stripped) plus trimmed args with `-y`/`--yes` dropped, or the URL with lowercase scheme/host and no trailing `/`; same-name pairs are not duplicates. The sprawl finding points at the first server/tool past the budget; tool waste is the tokens of the excess definitions, server findings carry none (their tool schemas are unknown offline). AI-EFF-006 reports a long skill body at its 501st line, with the tokens past it as waste.
Consequences: an unfenced JSON/YAML dump is caught only by the table/code checks; servers that differ only in package version are not duplicates.

## ADR-031 — Directives and aggregation for the style rules (AI-EFF-007, AI-COG-002/004) (2026-10-20)
Context: AI-COG-002 and AI-COG-004 count "directive sentences", but the AI-COG-001 extractor only keeps sentences with a polarity marker and an object, so "Write clean code." or "IMPORTANT: run the tests" would not count. The spec also leaves the anchor test, the summary location and which filler hits count open.
Decision: for the style rules a directive is a sentence (same splitting as AI-COG-001) with an AI-COG-001 marker anywhere or a verb from `IMPERATIVES` / `style::DIRECTIVE_VERBS` opening a clause (first word, or after `:` `,` `(`). The shared helper `util::aggregate` reports ≥ 3 hits as one finding at the first hit, with the rule's severity, the summed `token_waste` and the 3 most frequent quotes; fewer hits are Info each. AI-EFF-007 matches on normalized text at word bounds, skips code blocks, and the longest phrase wins (`make sure to always` → `always`); waste is `estimate(phrase) − estimate(replacement)` with the asset's calibration. AI-COG-002 anchors are a digit, a backtick, a `/`, a word containing `.` (file names) or "e.g."/"i.e."/"example"/"such as"; one hit per sentence, at its first vague term. AI-COG-004 checks caps words case-sensitively, ignores words in code spans, and reports once at the first emphasized directive.
Consequences: a sentence like "Some tests need Docker" is not a directive and is not checked; a vague directive that mentions any file name passes.

## ADR-032 — Negative-only, routing and structure heuristics (AI-COG-003/006/007) (2026-10-20)
Context: AI-COG-003's cue list misses alternatives phrased as a contrast or an imperative clause, and `use` itself appears in "never use X". AI-COG-006's cue list is literal, but the common form is "Use this agent when …" or "Use after a change". AI-COG-007 doesn't define "paragraph".
Decision: AI-COG-003 checks the negative directives of the AI-COG-001 extractor; an `instead`/`use`/`using`/`prefer`/`rather` word counts as an alternative unless one of the 2 words before it is a negator. FP guards in the same sentence: the negator follows `,`/`—`/`–` and the sentence doesn't open with a qualifier (contrast), or a later clause opens with a non-negated imperative (`IMPERATIVES`/`DIRECTIVE_VERBS`, which gained `redact`, `replace`, `wrap`). Hits aggregate with `util::aggregate` (ADR-031). AI-COG-006 cues: a word starting with `trigger`/`invok`/`proactive`; `use`/`used` opening a sentence or followed within 4 words by `when`/`whenever`/`for`/`if`; `when`/`whenever`/`if` + optional article + `user`. First person is `I`, `I'm`, `I'll`, `I've`, `I'd` (case-sensitive) outside double/curly quotes and code spans. One finding per asset at the `description` line, listing the reasons; a missing/empty description is left to AI-STR-001. AI-COG-007 counts body lines like AI-EFF-006; paragraphs are the Markdown view's paragraphs (list items in tight lists, tables and code are not), words split on whitespace; long paragraphs are reported once per asset at the first one.
Consequences: short descriptions with a cue still fire (the spec's < 20 words is kept); "Don't hardcode paths. Read them from config." still fires (the next sentence has no cue word). The `mixed` test repo's one-word descriptions now produce four AI-COG-006 findings in the CLI and report snapshots.

## ADR-033 — Load-together groups for AI-COG-005 (2026-10-20)
Context: the spec lists what loads together but not how groups, ordering and report location work, and AI-COG-001's section guard treats each file's H1 title as a scope, which would hide almost every cross-file conflict.
Decision: the always-on group is every Always (after promotion) Instructions/ScopedInstructions asset, sorted by path, each followed by its transitive `@imports`; each nested (Conditional) `CLAUDE.md`/`AGENTS.md` forms a group with the always-on set, its nested ancestors (shallowest first) and itself, plus imports. Only pairs whose later file is new to the group are checked, a directive is reported at most once, and same-file pairs are left to AI-COG-001. Same-directory `CLAUDE.md`/`AGENTS.md` siblings are not grouped (different platforms). Across files, a directive under the document title (first heading, level 1) has no section scope. The exclusive sets come from `[rules.AI-COG-001] exclusive`; AI-COG-005 has no options of its own.
Consequences: root `CLAUDE.md` and `AGENTS.md` are compared even though some tools load only one of them; a scoped heading in both files (e.g. "## Frontend" / "## Scripts") still silences the pair.

## ADR-034 — JSON/SARIF reporter details and schema validation (P6.1) (2026-10-20)
Context: the card asks to validate SARIF against the 2.1.0 schema with `jsonschema` "or document a manual step if that crate is too heavy"; the spec leaves the JSON gate value types, `new` before baselines, and the SARIF rule list open, and `jsonschema` is not in the dependency table.
Decision: `jsonschema` 0.59 is a **dev-dependency** of `pulse-report` with `default-features = false` (no HTTP resolver): ~60 test-only crates, nothing in the binary. The OASIS schema is vendored at `crates/pulse-report/tests/schemas/sarif-schema-2.1.0.json` and the snapshot tests validate every rendered log (plus a negative case). JSON gate values are typed (strings for severities/ratings, numbers for ratios/tokens, `null` for none); `new` is always `true` until P6.3; `--min-severity` filters only `findings`/`results`. SARIF `rules[]` holds only rules with results (keeps logs small; GitHub needs only those), `help.markdown` is the embedded `docs/rules/<ID>.md` via `pulse_rules::docs(id) -> Option<&'static str>` (an `Option` rather than the card's bare `&str`, so custom rules fall through). `meta.generated_at` is formatted in-house (RFC 3339 UTC, seconds) to avoid a date crate.
Consequences: a new rule must be added to the `rule_docs!` list (the registry test fails otherwise). `cargo test` builds `jsonschema` once (slow first build in CI).

## ADR-035 — Baseline and new-code mode details (P6.3) (2026-10-22)
Context: the spec says ratings use new findings "when `--new-only`/baseline is active" and that metrics "show both", without defining what each switch filters or what happens without a baseline file.
Decision: new-code mode = `--new-only` or `gate.new_code_only`. In it, ratings and every gate condition use metrics computed over new findings; `Report.metrics` keeps covering every open finding and `Report.new_metrics` holds the new-code numbers (terminal/Markdown "New code" line, JSON `metrics.new_issues`, SARIF `baselineState` when a baseline exists). `--new-only` also removes baselined findings from the report; `gate.new_code_only` alone keeps them, marked as not new. A missing baseline file is not an error: every finding is new and `scan`/`ci` warn on stderr when new-code mode is on, so a first CI run before the baseline is committed still works. `--changed-since` narrows scope like `PATHS` (intersected with them); an empty change set scans nothing. It runs git with `-z` (no path quoting) in the root, rejects refs starting with `-`, and turns a missing git or a git failure into exit 2. `serde`/`serde_json` become dependencies of `pulse-engine` (already in the table).
Consequences: `pulse baseline` writes fingerprints of a full, unfiltered scan; reports keep their schema version (`new_issues` and `baselineState` are additive).

## ADR-036 — Custom rule compilation and metadata (P6.5) (2026-10-22)
Context: the `Rule` trait and `Finding` carry `&'static` metadata and IDs, but custom rules come from `pulse.toml` at runtime; the spec doesn't say how a custom rule is located, categorized or overridden, and `CustomRule` only had `pattern`.
Decision: `pulse_rules::custom::compile` turns `[[custom_rules]]` into `Custom` rule objects owned by the engine's resolved rule set (run after the built-ins). Their `RuleMeta` and strings are leaked once per distinct value through an intern table, so repeated scans with one config don't grow memory. `CustomRule` gains optional `phrases` and `max_tokens`; `pulse-core` validation requires exactly one matcher and unique IDs. `RuleMeta.category` is a placeholder for custom rules; reports and `pulse rules` derive the category from the ID (`category_of`, `None` for `X-`). `[rules]` severity/off/`enabled` apply to custom IDs; other keys in a `[rules.X-…]` table are errors. Custom findings are inline-suppressible and never quote the match.
Consequences: custom rules don't affect ratings or context debt (no category, no `token_waste`); `pulse explain X-…` still reports an unknown rule (no doc); a broad `pattern` (e.g. `.`) reports every match (no per-asset cap).

## ADR-037 — Performance hardening and the robustness budget (P7.1) (2026-10-24)
Context: P7.1 asks that random bytes, huge lines, deeply nested JSON and 10k HTML comments "not exceed 2× the time budget", without saying which budget or at what size. The first hostile corpus took 42 s: libyaml's scanner is quadratic in flow-collection depth (100k `[` in frontmatter: ~39 s before `serde_yaml_ng`'s recursion limit trips), and AI-COG-001's pairwise directive loop, finding fingerprints (copying and hashing the whole line per finding) and `LineIndex::location` (counting chars from line start per finding) were quadratic on one huge line.
Decision: the robustness corpus is `benches/support/hostile.rs`: 12 generated assets, ~5 MB, each under `scan.max_file_bytes`, covering all four cases plus nested YAML/Markdown. Its budget is set by ADR-038 and enforced by `scripts/bench.sh`. `tests/robustness.rs` asserts no panic, every asset read, and 100 ms in release test builds; in debug it only guards against blow-ups (60 s; the corpus took 339 s before the fixes). Frontmatter whose flow collections nest deeper than 128 (the parser's own limit) is rejected by a linear pre-check with the parser's message, `recursion limit exceeded`, without parsing. Fingerprint occurrence counters are keyed by the xxh3 digest of `rule\0rel\0text\0` instead of the strings; values are unchanged (a 64-bit collision would only share a counter). `bench.sh` takes `BENCH_SLACK` (default 1.2), and CI runs it as a non-blocking `macos-14` job. A `profiling` cargo profile (release + symbols) and the `scan_loop` example support sampling profilers.
Sentence segmentation and word tokenization move to `pulse_core::text::prose` and are cached per asset (`Asset::prose()`), shared by AI-COG-001/002/003/004 and AI-SEC-010 (`cognitive::directives` re-exports the helpers).
Consequences: CI's macOS runner is a 3-vCPU VM that runs `typical` about as fast as the 2019 i5, so its numbers are a regression signal, not a check of the laptop budget. AI-COG-005 still compares directives pairwise across files (backlog).

## ADR-038 — Hardware-calibrated performance budgets (P7.1) (2026-10-24)
Context: the budgets are for an Apple M-series laptop, but `scripts/bench.sh` runs on whatever machine is at hand: a 2019 i5 locally, a 3-vCPU `Apple M2 Pro (Virtual)` runner in CI. Neither is the reference machine. Absolute budgets made every run red, so the numbers couldn't separate "slow machine" from "slow Pulse".
Decision: `bench.sh` times a fixed calibration workload first (`calibrate` example: a parallel walk of `typical` with Pulse's walker settings plus a parallel pass over 32 MB of prose that classifies every char and hashes each word in place, allocating nothing; none of Pulse's code; each part the minimum of 15 runs). It runs interleaved with the scenarios: each of 7 rounds calibrates (minimum of 5 runs per part), then times every scenario (minimum of 5 runs) and divides by that round's factor; the median over rounds is judged against the unscaled spec budgets. Pulse's own timings also take the minimum, so both sides of the ratio are measured the same way. It scales every time budget by factor = calibration ÷ reference calibration (`BENCH_REF_MS`), never below 1, so a fast machine is held to the spec and a slow one gets proportionally more time. Memory and binary size are not scaled. Startup is judged net of spawning `/usr/bin/true` (budget 1 ms, the 2 ms spec minus ~1 ms of spawn on the reference machine). The hostile budget becomes 2× the typical rate for the same content: 2 × 20 ms × (5 MB ÷ 2 MB) = 100 ms (it replaces ADR-037's 40 ms, which ignored size). The reference calibration is PROVISIONAL at 24 ms: the i5-8257U's ~47 ms halved, an estimate until one run on an M-series laptop pins it. Two earlier versions failed on CI. A CPU pass that built a lowercased copy of each chunk ran 2× slower on CI's VM than on the i5 while Pulse ran 1.5× faster there; the calibration must rank machines the way Pulse's own scan does. A short (8 MB) pass with medians then swung 7× between two CI runs (4.5 vs 31.7 ms) while Pulse moved ~20%; on a shared runner other load only adds time, so the minimum of a longer pass is the stable estimate. Calibrating only before and after the scenarios still let one CI run pass and the next fail on the same code (the runner's speed drifts within a run: calibration walk 16.9 → 11.3 ms while Pulse's typical went 24.6 → 27.0 ms); interleaving cancels that drift.
Consequences: a red bench now means "slower than the budget for this hardware". Until the reference is measured, the verdicts depend on that estimate. The calibration still moves about ±13% on a loaded laptop (thermal throttling); `BENCH_SLACK` covers part of it. Startup net of spawn also includes the OS loader mapping the binary, which the calibration does not model; it reads ~2.5 ms on the i5 and ~0.7 ms on CI.

## ADR-039 — Lexicon warm-up during discovery (P7.1) (2026-10-24)
Context: a fresh process scanning one small file spent ~7 ms in `rules` on the i5: building lexicon automatons and regexes on first use (secrets 3.6 ms, the AI-SEC-012 tool-call regex 2.7 ms, injection 2.4 ms, others ~3 ms). The first assets paid for them one after another, and the other workers blocked on the same `LazyLock`s. Optimizing rule logic barely moved `typical`, because this setup dominated the phase.
Decision: `pulse_rules::warm_up()` spawns one rayon task per costly lazy, and `scan` calls it right before discovery: the walk runs on `ignore`'s own threads while the rayon pool is idle, so the setup overlaps the walk. AI-SEC-003's per-provider regexes compile on demand (the `RegexSet` prefilter stays eager); compiling all of them up front doubled that lexicon's cost. Patterns are unchanged (switching the tool-call regex to ASCII classes would build faster but stop matching non-ASCII tool names).
Consequences: one-file scans go from ~12.5 to ~6.2 ms on the i5, and `typical` from ~43.5 to ~33.1 ms (`rules` 20.0 → 9.6 ms). Lexicons of disabled rules are still built in the background (a few ms of CPU off the critical path). Output is unchanged.

## ADR-040 — Release pipeline, GitHub Action and pre-commit hook (P7.2) (2026-10-24)
Context: the card asks for `cargo-dist` builds for five targets, shell/PowerShell installers, a Homebrew formula template, a composite action and a pre-commit hook, without fixing the build profile, how the formula is published or how pre-commit gets the binary.
Decision: `dist` 0.33.1 (`dist-workspace.toml`, generated `.github/workflows/release.yml`; tags `vX.Y.Z` release, pull requests run `dist plan`). Targets are exactly the card's: `aarch64`/`x86_64-apple-darwin`, `aarch64`/`x86_64-unknown-linux-musl`, `x86_64-pc-windows-msvc` (the glibc builds `dist init` adds were dropped: musl binaries run everywhere). `[profile.dist]` inherits `release` unchanged (fat LTO, one codegen unit), not dist's default thin LTO, so released binaries match the binary-size and speed budgets measured on `release`. The Homebrew installer targets the `SamueleMoscatelli/homebrew-tap` tap but has no publish job: `pulse.rb` is a release asset (the template) and pushing it to a tap is a manual step, so a release needs no tap repo or token. `action.yml` is composite: it downloads the runner's release archive (`version` input, default `latest`), checks its `.sha256`, optionally writes and uploads SARIF (`github/codeql-action/upload-sarif@v3`, category `pulse`), then runs `pulse ci` (GitHub format, job summary). `.pre-commit-hooks.yaml` declares one `language: system` hook (`pulse ci`, `pass_filenames: false`): the workspace root is a virtual manifest, which pre-commit's `language: rust` (`cargo install --path .`) cannot build, and project rules need the whole asset set anyway.
Consequences: the dist config is the source of truth; edit it and run `dist generate` (CI's `dist plan` fails on a hand-edited `release.yml`). The pre-commit hook requires a prior install. The first release needs a `v0.1.0` tag pushed by the maintainer; the action and README examples reference release tags.
