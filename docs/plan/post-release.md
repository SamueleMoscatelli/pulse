# Post-release follow-ups (v1.0.0)

Distribution and visibility steps left after v1.0.0 (released 2026-10-25). Not `/next-task`
cards: they are mostly GitHub settings and repo setup, done by the maintainer. Pick them up
once the improvements from the awesome-copilot testing are released.

## 1. Homebrew tap
- [x] Create the public repo `SamueleMoscatelli/homebrew-tap` (the name must start with `homebrew-`).
- [x] Commit the latest release's `pulse.rb` (a release asset generated by dist) as `Formula/pulse.rb`.
- [x] Test it on a `macos-latest` runner (the maintainer's Mac has no Homebrew):
      `brew install SamueleMoscatelli/tap/pulse && pulse --version`.
- [x] Add the Homebrew install line to the README.
- [x] Optional: let each release update the tap. In `dist-workspace.toml` add `publish-jobs = ["homebrew"]`,
      create a fine-grained token with write access to the tap repo only, store it as the
      `HOMEBREW_TAP_TOKEN` secret, run `dist generate` and commit the regenerated `release.yml`.
      Without this, copy `pulse.rb` to the tap by hand on every release.

A plain `brew install pulse` (homebrew-core) is not realistic yet. The `pulse` name is taken by
a cask (a system monitor), so core would need another name such as `pulse-cli`. Core also
requires notability (roughly 75+ stars, 30 forks or 30 watchers) and a build-from-source
formula, not dist's binary one. Revisit once there are users.

## 2. GitHub Marketplace listing
- [ ] Rename `name:` in `action.yml`: "Pulse" is rejected, because Marketplace names must be
      unique and must not match a GitHub user or org (`github.com/pulse` exists). For example:
      `Pulse AI Asset Quality Gate`. Existing `uses: SamueleMoscatelli/pulse@v1` keeps working.
- [ ] Ship the rename in the next release (the listing reads `action.yml` from the release tag).
- [ ] Prerequisites: 2FA on the account; accept the Marketplace Developer Agreement.
- [ ] Edit that release → tick "Publish this Action to the GitHub Marketplace" → categories
      Code quality, Security.

## 3. Usage tracking (no telemetry: Pulse is offline by design)
- [ ] Optional: a scheduled workflow that saves the 14-day traffic API numbers (views, clones,
      referrers) weekly, since GitHub drops older data.
- Signals to check from time to time:
  - release download counts per asset (the Linux x64 archive roughly counts Action runs):
    `curl -s https://api.github.com/repos/SamueleMoscatelli/pulse/releases | python3 -c 'import json,sys; [print(r["tag_name"], {a["name"]: a["download_count"] for a in r["assets"] if a["download_count"]}) for r in json.load(sys.stdin)]'`
  - Insights → Traffic (last 14 days only); Insights → Dependency graph → Dependents
  - stars, forks, watchers; issues and discussions
  - code search: `SamueleMoscatelli/pulse path:.github/workflows`, `path:.pre-commit-config.yaml`

## Every release from now on
1. PR: bump `version` in the root `Cargo.toml`, add the `CHANGELOG.md` section (`## X.Y.Z - date`),
   refresh the report snapshots (only the version line changes) and the README sample header.
2. Merge, then on an up-to-date `main`: `git tag -a vX.Y.Z -m "Pulse X.Y.Z" && git push origin vX.Y.Z`.
   A `-rc.N` suffix publishes a prerelease.
3. When the Release workflow is green, move the major tag:
   `git tag -f -a v1 -m "Pulse v1" 'vX.Y.Z^{}' && git push -f origin v1`.
4. Check that the Release workflow's `publish-homebrew-formula` job pushed `pulse X.Y.Z` to the
   tap and that the tap's `test` workflow is green (ADR-056). If it failed (e.g. an expired
   `HOMEBREW_TAP_TOKEN`), update the tap by hand: in the `homebrew-tap` clone, replace
   `Formula/pulse.rb` with the release's `pulse.rb`
   (`curl -fsSLo Formula/pulse.rb https://github.com/SamueleMoscatelli/pulse/releases/download/vX.Y.Z/pulse.rb`),
   commit `pulse X.Y.Z` and push. Its `test` workflow installs the formula on macOS (arm,
   Intel) and Linux. Skip this for `-rc.N` prereleases.
