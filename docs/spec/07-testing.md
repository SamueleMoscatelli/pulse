# 07 — Testing strategy

## Layers

| Layer | Where | Tooling |
|---|---|---|
| Unit | `#[cfg(test)] mod tests` next to the code | std, `insta` for complex values |
| Rule fixtures | `crates/pulse-rules/tests/fixtures/<RULE-ID>/` + one harness `tests/fixtures.rs` | harness below |
| Reporter snapshots | `crates/pulse-report/tests/` | `insta` (`assert_snapshot!`) |
| CLI end-to-end | `crates/pulse-cli/tests/` over `tests/fixtures/repos/*` | `assert_cmd`, `predicates`, `insta` |
| Performance | `crates/pulse-engine/benches/`, `scripts/bench.sh` | `divan`, `hyperfine` (optional) |

## Rule fixture harness

Layout per rule:

```
crates/pulse-rules/tests/fixtures/AI-SEC-002/
  fail_basic.md            # MUST produce >= 1 finding of AI-SEC-002
  fail_basic.md.expect     # optional: expected "line:col" per line, exact set match
  fail_obfuscated.md
  pass_code_example.md     # MUST produce 0 findings of AI-SEC-002
  _kind                    # optional: file containing the AssetKind to use (default: inferred from extension/name; see below)
```

- The harness iterates every fixture directory, builds an `Asset` with the kind from `_kind` (or inferred: `.md` → Instructions, `.mdc` → ScopedInstructions, `SKILL.md` → Skill, `.json` → McpConfig unless `_kind` says otherwise), and runs **only** the rule named by the directory (asset rules and project rules; for project rules every file in the directory forms the project).
- Failures print `fixture, expected, actual` compactly.
- The harness also asserts that every registered rule has a fixture dir with ≥ 1 `fail_*` and ≥ 1 `pass_*`, and a `docs/rules/<ID>.md`. Unimplemented rules are not registered, so this stays green phase by phase.
- Fixtures containing invisible characters are generated by the test (`\u{202E}` in Rust strings), not committed raw, so editors and git tooling don't mangle them. Put those cases in unit tests or in `fixtures.rs` helper cases. When every fail case of a rule is generated, a `_generated` file in its fixture dir (naming the tests) stands in for the `fail_*` requirement.

## Snapshot policy

`insta` snapshots are reviewed, not blindly accepted: after `cargo insta test`, read each `.snap.new` diff and accept only if it matches the spec. Never run `cargo insta accept` without reading the pending snapshots.

## Performance checks

- `divan` benches (`crates/pulse-engine/benches/scan.rs`): estimator throughput, normalize throughput, full `scan()` over the `large` repo generator (`benches/support/gen_repo.rs`, synthesized at bench time in a tempdir: 1,000 assets among 10,000 files).
- `scripts/bench.sh` builds release, synthesizes `typical` (200 assets, 20k files) and `large` (1,000 assets, 200k files) under `target/bench-repos/` with the `gen_repo` example, and takes the minimum wall time of `pulse scan -q` (as the calibration does; it also prints `typical`'s median `--timings` phases) (hyperfine if available, else a Perl `Time::HiRes` loop; `/usr/bin/time` only for peak RSS). It also regenerates `hostile` (`gen_repo <DIR> hostile`, see Robustness). Before timing, it runs the `calibrate` example (a parallel walk of `typical` plus a parallel text pass, using none of Pulse's code) interleaved with the scenarios: in each of `BENCH_ROUNDS` (7) rounds it calibrates, times every scenario, and divides each time by factor = calibration ÷ `BENCH_REF_MS` (the reference machine's calibration, never below 1); the median over rounds is judged against the spec budgets. `BENCH_FACTOR` overrides the factor. It fails if a budget is exceeded by more than `BENCH_SLACK` (default 1.2, i.e. 20%). CI runs it as a non-blocking job on `macos-15` (Apple M-series; `macos-14` images retire on 2026-11-02). Numbers are recorded in `docs/perf.md`.
- Robustness (ADR-037): `crates/pulse-engine/tests/robustness.rs` scans a generated corpus of hostile assets (`benches/support/hostile.rs`: 512 KiB of random bytes as Markdown and JSON, one 512 KiB line, JSON/YAML/Markdown nested 100k deep, 10k HTML comments). It must not panic, must read every asset, and must finish within 2× the typical budget for the same content, 2 × 20 ms × (5 MB ÷ 2 MB) = 100 ms on the reference machine; `bench.sh` enforces it (ADR-038).
- Profiling: `cargo build --profile profiling -p pulse-engine --example scan_loop`, then sample `scan_loop <DIR> [N]` (N in-process scans) with `samply`, `cargo flamegraph` or macOS `sample`.
